# 0042. Signal のグループへの投稿の判定と本人の承認は、配置が選んだときだけ、Signal のプラグインの中で Signal で行う

- Date: 2026-11-18
- Status: Accepted

## Context

Signal のプラグインは、許したグループに、エージェントの投稿を判定も承認も通さずに送る（ADR-0041）。natsumi は、Slack への投稿を判定（ポッポさん。Jev の API に、本人に代わる約束・期限、隠しごとの匂わせ、事実と違う説明、同意の捏造、私的な事情の 5 つを点数で聞く。natsumi ADR 0039・0040）に通していた。Signal のグループでも、オーナーの名で出る投稿を同じように判定し、迷うものは本人に聞いてから送りたい。知らないグループに足されたときも、本人に聞き、断られたら抜けてブロックしたい。

penelope で、これに当たる仕組みは次のとおりである。

- 投稿の中身の判定は、core には置かない。Slack への投稿の判定は、後で Sentinel の `slack.com` のコネクタに足すことを見込んでいる（ADR-0028 の「本 ADR で決定しないこと」、ADR-0033）。
- 承認待ちは Sentinel が持ち、オーナーは Web UI で答える（ADR-0005）。ただし最初の版の Sentinel は承認を持たない。`default: ask` は使えない（[Sentinel の設定](../sentinel-config.md)）。
- Signal への送信は、Sentinel を通って Signal のプラグインの送り口に届く（ADR-0040）。Sentinel から見ると、送り口は Pod の中の Unix socket の上流である。
- Signal では、連絡先の誰かがエージェントを承認なしにグループへ足せる。

## Decision

本 ADR は、Signal のプラグインに、グループへの投稿の判定と本人の承認、知らないグループの問い合わせを、設定で選べる形で足す。ADR-0005（Sentinel の承認待ち）と ADR-0033（core に判定を置かない）は変えない。

### 1. 配置が選んだときだけ

- 設定の `approvals: true` のときだけ動く。無ければ、ADR-0041 のとおり判定も承認も無い。
- 判定（`judge`）は、`approvals: true` の上で、さらに選べる。無ければ、グループへの本文のある投稿は全部本人に回す。

### 2. グループへの投稿は、判定して、送る・突き返す・本人に回す

- 判定の点数のどれかが `return_at` 以上なら、送らずにエージェントに突き返す。`ask_at` 以上なら本人に回す。どれも下なら送る。判定が答えなかったときは本人に回す。同じ宛先で続けて突き返したら、その次は本人に回す。
- 本文の無い、ファイルだけの投稿と、1 対 1 の `senders` への送信は、判定も承認も通さない。

### 3. 本人には Signal で聞き、答えはエージェントに渡さない

- 本人（`senders` の最初）の 1 対 1 に、下書きと理由と期限を送る。本人は 👍・👎・❌ のリアクションか、引用した返事で答える。
- 本人の答えは、エージェントに出来事として渡さない。決まったら、プラグインが送るか捨て、エージェントにはグループの `stream` に結果の出来事を入れる。
- 期限が過ぎたら送らない。

### 4. 知らないグループは、本人に 1 度聞く

- `groups` に無いグループに足されたことを見つけたら、本人に 1 度聞く。参加なら決まった形の名前で受けるグループに足し、断るか 24 時間答えが無ければ、抜けてブロックする。

### 守る対象と、失敗したときの倒し方

- 守る対象は、オーナーの名で、オーナー以外の人が読むグループに出る投稿である。
- 判定が答えないとき、本人に聞けないときは、送らない側に倒す。
- 本人の答えは、エージェントの会話を通らない（ADR-0005 の Decision と同じ考え）。
- 回した投稿と、グループへの答えは、設定のファイルに持つ。無ければメモリだけで、立ち上がり直すと消える。
- 判定の API への問い合わせは receivers の外向きで、Sentinel を通らず、記録に残らない（ADR-0028 の Consequences）。判定には、グループの名前と直近の発言と下書きを送る。

### 本 ADR で決定しないこと

- 設定の欄と既定、判定の問いの文、本人への文面、答えの言葉（委譲先: [receivers の仕様書](../receivers.md) の「グループへの投稿の判定と本人の承認」）
- Sentinel が承認待ちを持つようになったとき、この承認を Sentinel と Web UI へ移すか（委譲先: Sentinel の既定を ask に切り替えるときの ADR）
- 本人が下書きを直して送ること

## Consequences

- natsumi が Slack への投稿に使っていた判定を、Signal のグループへの投稿にも使える。
- 承認待ちの仕組みが、Sentinel（ADR-0005、まだ無い）と Signal のプラグインの 2 か所にできる。Signal の承認は Web UI に出ない。
- 判定の外部 API に、オーナー以外の人の発言の一部が送られる。その通信は Sentinel の記録に残らない。
- Signal に固有の仕組み（リアクションで答える、グループに入る・抜ける）は、プラグインにだけある。

## Alternatives Considered

- **Sentinel のコネクタで判定し、承認待ちを Sentinel に持つ（ADR-0005）**: 承認待ちと Web UI の答えの口がまだ無い。Signal の送り口は Sentinel から見ると Pod の中の上流で、宛先と本文の意味は Signal のプラグインしか知らない。知らないグループの問い合わせは、そもそも送信ではない。Sentinel に承認待ちができたら移すかを決め直す（本 ADR で決定しないこと）。
- **判定も承認もしない（ADR-0041 のまま）**: グループへの投稿が、エージェントの判断だけで出る。判定を使ってきた配置では、守りが減る。
- **承認を Web UI で答える**: 本人は Signal で話しているので、Signal で答えられる方が早い。Web UI の承認は ADR-0005 の仕組みを待つ。
