# 0030. 裏の仕事は runner が道具で起こし、終わったら出力の末尾を持つ出来事を本体に入れる

- Date: 2026-11-16
- Status: Accepted

## Context

エージェントは、Pi の基本のツールの bash でコマンドを動かす（ADR-0001）。bash はコマンドが終わるまで返らないので、長いコマンド（テストの一式、VM の上の作業、ほかのエージェントの返事を待つこと）を動かすと、そのターンはその間止まる。終わりを待たずに `&` で裏に回すと、終わったことを知る道が無い。

ほかのエージェントへの A2A の頼みは、sandbox の A2A の CLI で送る（ADR-0011）。頼んだ相手の返事は、Task を読みに行かないと分からない。確かめた事実は次のとおりである（References）。

- fraction-agents の係も、penelope の A2A の受け口も、Agent Card の `capabilities.streaming` が false で、Task の更新を流す呼び出しを持たない。penelope の受け口は、流す呼び出しを断る（ADR-0018 の Decision 項 1（受け口は backend の外向きの待ち受けに置き、A2A 1.0 で受ける））。
- A2A の CLI の `a2a task get` は `--wait` で、Task が終わるか聞き返しの状態になるまで、`--poll-interval` の間隔で読み直して待つ。全体の待ちの上限は `--timeout` である。流す呼び出しが無い相手にも効く。CLI には、流す呼び出しで待つ `a2a task subscribe` もある。

natsumi は、`run_shell` に待つ秒数を足し、過ぎたらコマンドを裏に回して、終わったら知らせる形にしていた（natsumi ADR 0094）。待つ数に上限（既定 5）を置き、1 つのコマンドを待つのは 24 時間までとしていた。

penelope には、サブエージェントが止まったことを本体に知らせる道がある（ADR-0022）。runner が sandbox 向けの口の自分宛ての出来事（受信元 `self`）を入れ、中身は `/sources/self/<名前>/` に追記され、本体のターンには要約と場所が入る。

## Decision

適用範囲は、本体のセッションがコマンドを裏で動かし、その終わりを知ることである。Pi の bash の動き、サブエージェント（ADR-0022）は変えない。

### 1. 裏の仕事は、runner が渡す道具で起こす

- runner は、本体のセッションに、コマンドを裏で起こす道具、走っている裏の仕事の一覧、裏の仕事を止める道具を渡す。起こす道具は、コマンドを起こしたらすぐ返る。
- 裏の仕事は、sandbox の中で、エージェントと同じユーザーで動く。外向きは、ほかの通信と同じく Sentinel を通る（ADR-0003）。
- 道具はサブエージェントには渡さない。終わりの知らせが届くのは本体だけだからである。
- コマンドの標準出力と標準エラー出力は、すべて HOME の永続する場所のファイルに書く。起こす道具の結果に、そのファイルの場所を返す。

### 2. 終わったら、runner が本体宛ての出来事を入れる

- 裏の仕事が終わると、runner が sandbox 向けの口で、本体宛ての出来事を 1 件入れる。中身は、終わり方（exit code か、止めたシグナルか、時間切れか、中断か）、コマンド、かかった時間、出力の末尾、出力のファイルの場所である。
- 出力の末尾は、上限の字数までにする。全文はファイルにある。
- 受信元は、サブエージェントの知らせの `self` と分ける。backend の設定で inline を別に選べるようにするためである（ADR-0013 の Decision 項 2（ターンには要約と場所だけを渡す））。既定では、裏の仕事の終わりは inline とし、中身ごとターンに入る。サブエージェントの知らせは今のまま要約と場所である。
- 渡す時の既定は `now` とする（ADR-0013 の Decision 項 3（渡す時は受信元の側が出来事ごとに決める））。
- 同じ終わりを送り直しても、backend が `id` で重複を落とす。

### 3. 数と長さに上限を置く

- 同時に走る裏の仕事の数に上限を置く。上限に達しているときは、起こす道具が断り、走っている仕事を返す。黙って待たせたり、知らせの無いまま走らせたりしない。
- 1 つの裏の仕事の長さに上限を置く。起こすときに短い上限を選べ、選ばなければ設定の上限である。上限に達したら、runner はそのコマンドのプロセスのまとまりを止め、時間切れとして知らせる。終わらないコマンドが枠を埋め続けないためである。
- 上限の値は runner の設定で決める。

### 4. 夜の切り替えと、runner の立ち上がり直し

- 夜の切り替え（ADR-0007）のときに走っている裏の仕事は、止めずに走らせる。終わりの出来事は、翌日のセッションの本体に届く。
- runner は、走っている裏の仕事を HOME の永続する場所に記録する。runner が立ち上がり直したら、前に走っていた裏の仕事を中断として知らせ、残っているプロセスのまとまりは止める。runner が見ていない間の終わり方は確かめられないためである。

### 5. A2A の返事を、裏の仕事で待つ

- ほかのエージェントの返事を待つときは、裏の仕事で `a2a task get --wait` を走らせる。返事が来るか聞き返しになるとコマンドが終わり、その出力の末尾が出来事として本体に届く。backend にも runner にも、A2A のための仕組みは足さない。
- 待ちの上限は、CLI の `--timeout` と裏の仕事の上限の短い方になる。
- 頼む相手と penelope の A2A の受け口が Task の更新を流せるようになったら、待ち方を `a2a task subscribe` に替え、流れが切れたときは `a2a task get --wait` に戻る。そのための受け口の変更は、ADR-0018 を改める別の ADR で決める。
- 使い方は、A2A のコネクタの文書に書く（ADR-0020）。プロンプトには書かない（ADR-0008）。

### 守る対象と、失敗したときの倒し方

- 裏の仕事は、bash で動かすコマンドと同じ権限で動く。守る対象と鍵の扱い（ADR-0003・ADR-0004）は変えない。
- 終わりの出来事を backend に入れられなかったときは、runner が同じ `id` で送り直す。
- 起こす道具は、上限を超えるときと、作業の場所が無いときは、コマンドを起こさずに理由を返す。

### 本 ADR で決定しないこと

- 道具の名前・引数・説明の文面、出力のファイルの置き場所、記録の形（委譲先: runner のコード `packages/runner/src/tools.ts` と `packages/runner/src/prompts.ts`。ADR-0008 の方針に従う）
- 受信元の名前、`payload` の欄、`id` の付け方、末尾の字数・同時の数・長さの上限の既定（委譲先: [sandbox 向けの口の仕様書](../sandbox-api.md) の「自分宛ての出来事」と [出来事の仕様書](../events.md)）
- `a2a task get --wait` の書き方の例（委譲先: 配置のリポジトリの A2A のコネクタの文書）
- A2A の受け口が Task の更新を流すこと（委譲先: ADR-0018 を改める ADR）
- サブエージェントにも裏の仕事の道具を渡すこと（委譲先: 要るとなったときの新しい ADR）

## Consequences

- エージェントは、長いコマンドを裏に回して、その間もオーナーや出来事に答えられる。終わったことは出来事で届き、出力の末尾がターンに残る。
- A2A の返事の待ちに、新しい仕組みが要らない。相手が流す呼び出しを持たなくても、CLI の待ちで足りる。
- 終わりの出来事は inline で残るので、畳んだ後も、何が終わってどうだったかが文脈に残る。代わりに、裏の仕事の数だけ文脈が伸びる。末尾の上限で抑える。
- 待ちの間、CLI は間隔ごとに相手の Task を読み直す。相手への呼び出しは、流す形より多い。
- runner が立ち上がり直すと、走っていた裏の仕事は止まる。長い仕事は、版上げや Pod の作り直しで切れることを受け入れる。
- 上限を超える数の仕事は起こせない。エージェントは、終わるのを待つか、止めて起こし直す。

## Alternatives Considered

- **natsumi と同じく、bash に待つ秒数を足し、過ぎたら裏に回す**: Pi の基本のツールを変えることになる（ADR-0001 の「Pi の基本のツールはそのまま使う」）。道具を分ければ、bash はそのままでよい。
- **終わりをサブエージェントの知らせと同じ受信元 `self` で送る**: inline を選ぶ単位が受信元なので、サブエージェントの知らせ（最後の地の文の全文）まで inline になるか、裏の仕事の末尾が要約と場所になるかのどちらかになる。
- **A2A の返事を backend が Task を読みに行って出来事にする**: backend が sandbox の送った Task を知る道と、相手の鍵が要る。sandbox の CLI で待てば足りる。
- **A2A の push の受け口を作る**: 受け手に公開の URL と、依頼ごとの token を出す道が要る。待ちで足りる間は作らない。
